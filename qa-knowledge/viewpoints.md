# 28観点リスト(QA Explorer の地図)

このファイルは QA Explorer エージェントが「どの観点でテストするか」を判断する
最上位の知識源です。観点ごとに **対象機能・考慮すべき仕様・狙うバグ・優先度** を
記述しています。

エージェントはこのファイルを起動時に必ず読み込み、各観点の「狙うバグ」を頭に入れた
うえでテストを設計してください。

## P0: 必ず最初に消化する観点

### 観点 02: 表示(UI) - エラー表示(正常系)
- **対象**: バリデーションを行うすべての入力フォーム
- **考慮すべき仕様**:
  - 必須項目未入力時に明確なエラーメッセージが出る
  - メッセージで「何が問題か / なぜか / どうすればよいか」が伝わる
  - フィールドごとにエラーが表示される(全体に1つだけではない)
  - メッセージが当該言語(例: 日本語サイトなら日本語)で表示される
  - エラー時に該当フィールドへフォーカスが移動する
- **狙うバグ**:
  - メッセージが曖昧(「エラーが発生しました」だけ)
  - 内部エラーコードが画面に漏れる(`ERR_001` など)
  - 修正後に再送信できない・どこを直せばいいか分からない

### 観点 10: 動作確認 - 単機能
- **対象**: 各機能の Must / Never 条件
- **考慮すべき仕様**:
  - 主要ボタン・リンクが仕様通りに動く
  - 一連のフロー(例: 一覧→詳細→申込)で遷移とデータ引継ぎが成立
  - 戻るボタンで入力内容が保持される
- **狙うバグ**:
  - 機能不動作・遷移失敗・データ消失

### 観点 11: 状態遷移 - イベントによる状態変化
- **対象**: ボタン押下・送信などのイベントによる画面・状態の変化
- **考慮すべき仕様**:
  - クリック → 適切な遷移
  - 送信 → 確認画面
  - 戻る → 元の画面に状態保持
- **狙うバグ**:
  - 遷移失敗・データ消失・無限ループ

### 観点 23: 排他処理 - 禁則
- **対象**: 業務ルール上、許されない操作
- **考慮すべき仕様**(対象システムに合わせてエージェントが具体化):
  - 過去日付の指定不可
  - チェックイン日 > チェックアウト日の不可
  - 上限を超える数量の指定不可
- **狙うバグ**:
  - 禁則チェック漏れ
  - クライアント側だけでチェックしていてサーバ側で素通り
- **境界の注記**: 本観点は **「値」の禁則** に限定する。
  「いつ操作できるか(時)」は観点27、「誰が操作できるか(人)」は観点28で扱う。

### 観点 26: CRUD - 削除と参照整合
- **対象**: リソースを消すすべての操作(削除・取消・退会・解除。論理削除を含む)
- **考慮すべき仕様**:
  - 削除後、一覧・検索結果・関連画面・集計・通知から消える
  - 削除済みリソースのURL/IDへ直接アクセスしたとき、404 もしくは権限エラーになる
  - 親子関係のあるデータで、親を削除したときの子の扱い
    (カスケード削除 / 削除拒否 / 孤児化のどれが仕様か)
  - 削除確認のガードがあり、キャンセルすると消えない
  - 同じリソースを2回削除してもエラーにならない(冪等)
- **狙うバグ**:
  - 一覧からは消えたが、検索・通知・件数・キャッシュに残る
  - 親削除で子が孤児化し、参照時に500
  - 削除済みIDへの直アクセスで内部エラー・情報漏洩
  - 確認なしで即削除される(不可逆操作のガード不足)

### 観点 28: CRUD - 操作可能ユーザー(認可)
- **対象**: C/R/U/D すべての操作に対する「誰が実行できるか」
- **前提条件**: 別所有者・別ロールの認証状態が最低2者分必要。
  用意できない場合は **実施せず `manual-tests.md` に起票して人間に移譲する**
  (「アカウントが無いのでN/A」で閉じない)
- **実施環境の制約**: 他人のデータへの到達を試みるテストのため、
  **検証環境のテストアカウント間でのみ実施する**。本番・共有環境では実施しない。
- **考慮すべき仕様**:
  - 所有者本人 / 同一グループ / 管理者 / 一般ユーザー / 未ログイン それぞれの可否
  - UIでボタンが非表示なだけでなく、URL直打ち・API直叩きでも拒否される
  - 他人のリソースIDに差し替えた場合に拒否される(水平権限昇格 / IDOR)
  - **Read の認可**: 一覧に出ないデータが直リンクで見えてしまわないか
  - 権限剥奪・退会・ログアウト後に、既存セッションで操作が通らないか
- **狙うバグ**:
  - 他人のリソースをID差し替えで参照・更新・削除できる(最優先)
  - UIガードのみでサーバ側の認可チェックが無い
  - 権限なしの応答が404でなく、リソースの存在を推測できる情報を返す

## P1: 次に消化する観点

### 観点 03: 入力 - 文字種
- **対象**: 氏名・自由記述・住所などのテキスト入力
- **考慮すべき仕様**:
  - ひらがな・カタカナ・漢字・半角英数・全角英数・記号・スペース
  - 絵文字(サロゲートペア)・サニタイズ対象文字(`<`, `>`, `&`, `"`, `'`)
  - 制御文字(タブ・改行)
- **狙うバグ**:
  - 特殊文字でSQLインジェクション・XSS・サニタイズ不足
  - サロゲートペアでクラッシュ・文字化け
  - バリデーション不足で予期しない値がDBに入る

### 観点 07: 入力 - 数値(正常値)
- **対象**: 数値入力フィールド(個数・金額・宿泊数など)
- **考慮すべき仕様**:
  - 仕様範囲内の値(下限・中央値・上限)が入力可能
  - 整数のみ / 小数許容の区別
- **狙うバグ**:
  - バリデーションが効きすぎて正常値が弾かれる

### 観点 24: CRUD - 生成と一意性
- **対象**: リソースを作るすべての操作(新規登録・追加・申込・投稿)
- **考慮すべき仕様**:
  - 作成直後に一覧・検索・詳細へ反映される
  - 一意制約のある項目で重複作成を試みたときの挙動とメッセージ
  - 連打・リトライで多重作成されない(観点12が画面側、本観点は **永続データ側** を確認)
  - 作成上限がある場合の 上限ちょうど / 上限+1
  - 作成失敗時に中途半端なレコードが残らない
- **狙うバグ**:
  - 一意制約違反が500で返る / 内部エラーがメッセージに漏れる
  - 作成は成功するが一覧に出ない(キャッシュ・インデックス遅延)
  - 失敗したはずの作成が部分的に成立している

### 観点 25: CRUD - 更新と競合
- **対象**: 既存リソースを書き換えるすべての操作(編集・変更・ステータス更新)
- **考慮すべき仕様**:
  - 1項目だけ更新したとき、**画面に出ていない項目が消えない**(部分更新 vs 全体上書き)
  - 更新内容が関連する全画面(一覧・詳細・検索・通知・集計)に伝播する
  - 同じリソースを2タブ/2セッションで開いて両方更新したときの挙動
    (楽観ロックで弾くか、後勝ちか、後勝ちなら警告があるか)
  - 更新経路でもバリデーションが効く(作成時にしか検証していないケース)
  - 更新前後で変わってはいけない項目(ID・作成日時・作成者)が不変
- **狙うバグ**:
  - 画面に無い項目が null で潰れる
  - 後勝ちで他人の変更が警告なく消える
  - 作成時は弾かれる値が、更新経路からは通る

### 観点 27: CRUD - 操作可能期間
- **対象**: 「いつから / いつまで」の制約がある操作(締切・公開期間・開始前後)
- **考慮すべき仕様**:
  - 期間境界ちょうど(締切時刻と同時刻)の可否
  - 境界の前後(1分前 / 1分後)
  - 端末の時刻を変えても判定が変わらない(サーバ時刻で判定している)
  - タイムゾーン(JST / UTC)の取り違え
  - 期間内に画面を開いたまま期間外になってから送信した場合
  - 期間外操作のエラーメッセージの質(観点02と連結)
- **狙うバグ**:
  - 境界の off-by-one(締切ちょうどの可否が仕様と逆)
  - クライアント時刻を信頼しており、端末時刻の変更で突破できる
  - TZ混在で9時間ずれる
  - 期間外の送信が無言で成功する / 無言で失敗する
- **実行方針**: ブラウザ側の時刻は Playwright の `page.clock` で操作できるが、
  **サーバ側で判定しているものは自動化不可**。その場合(および期間設定の変更に
  管理画面操作が必要な場合)は `manual-tests.md` に起票して人間に移譲する。

## P2: 標準消化対象の観点

### 観点 01: 表示(UI) - レイアウト/文言
- **対象**: 画面全体のレイアウト
- **考慮すべき仕様**:
  - 画面幅(モバイル375 / タブレット768 / デスクトップ1920)でレイアウト崩れなし
  - 文字切れ・折返し不良なし
  - 必須バッジ等が見える
- **狙うバグ**:
  - レスポンシブ崩れ、文字切れ、画像比率の崩れ

### 観点 04: 入力 - 文字数(正常値)
- **対象**: テキスト入力の通常使用範囲
- **考慮すべき仕様**: 1文字 / 中央値 / 通常上限の範囲
- **狙うバグ**: バリデーション不足、UIで文字数表示なし

### 観点 05: 入力 - 文字数(正常限界)
- **対象**: 仕様上の上限・下限
- **考慮すべき仕様**: 最小境界値・最大境界値ちょうどの値
- **狙うバグ**: 境界値エラー(off-by-one)

### 観点 06: 入力 - 文字数(異常値)
- **対象**: 仕様外の文字数
- **考慮すべき仕様**: 上限+1・大幅超過(例: 10000文字)
- **狙うバグ**: バッファオーバーフロー、DB側のtruncate、エラー応答なし

### 観点 08: 入力 - 数値(異常値)
- **対象**: 数値の異常パターン
- **考慮すべき仕様**: 負数、ゼロ、上限超過、小数点(整数欄に)、文字列、`NaN`、`Infinity`、空文字、指数表記
- **狙うバグ**: 計算エラー、DB型違反、想定外の処理経路

### 観点 09: 入力 - 未入力
- **対象**: すべての必須項目
- **考慮すべき仕様**: 空文字 / スペースのみ / 全角スペース のみ
- **狙うバグ**: 必須チェック漏れ、空白文字を「入力済み」と判定

### 観点 12: 状態遷移 - 経時変化
- **対象**: 非同期処理中・処理後の状態
- **考慮すべき仕様**:
  - 送信中はボタン無効化
  - 二重送信防止
  - ローディング表示
  - タイムアウト時の挙動
- **狙うバグ**: 二重送信でデータ重複、ローディング表示なしでユーザー混乱
- **境界の注記**: 本観点は **非同期処理中の画面挙動** に限定する。
  業務上の「操作可能な時間枠」は観点27で扱う。

### 観点 13: 画面遷移 - 切替えとデータ保持
- **対象**: 画面遷移時のデータ保持
- **考慮すべき仕様**:
  - 確認画面から戻った時にフォームデータが保持
  - ブラウザの戻るボタンでも保持
- **狙うバグ**: データ消失、再入力強制

### 観点 14: 設定保持 - 初期値
- **対象**: 起動時・初回表示の状態
- **考慮すべき仕様**: デフォルト値、ログイン状態での初期表示
- **狙うバグ**: 不適切なデフォルト、初期化エラー

### 観点 15: 設定保持 - 変更・反映
- **対象**: 入力内容が他画面に反映されるか
- **考慮すべき仕様**: フォーム入力 → 確認画面に反映、人数変更 → 料金に反映
- **狙うバグ**: 反映漏れ、古いデータ残留
- **境界の注記**: 本観点は **1フローの中での画面間の反映** に限定する。
  永続化されたデータの更新は観点25で扱う。

### 観点 17: 設定保持 - キャンセル
- **対象**: キャンセル操作後の状態
- **考慮すべき仕様**: 戻る操作ではデータ保持、ブラウザクローズでクリア
- **狙うバグ**: キャンセル処理不備、意図しないデータ残留

### 観点 18: 機能組合せ - 複数因子
- **対象**: 複数フィールドの組み合わせ
- **考慮すべき仕様**: ペアワイズ法で代表的な組合せをテスト
- **狙うバグ**: 特定の組合せでのみ発生する不具合

## P3: 余裕があれば消化する観点(同時実行・割込み系)

### 観点 19: 同時実行 - 登録と参照
- **対象**: DB登録と参照の同時実行
- **狙うバグ**: 排他制御不足、データ不整合

### 観点 20: 同時実行 - 複数アカウント
- **対象**: 別環境・同一アカウントから同時操作
- **狙うバグ**: ダブルブッキング、セッション混在

### 観点 21: 割込み - 別デバイス
- **対象**: PC + スマホで同時ログイン
- **狙うバグ**: 予期しないログアウト、セッション混在

### 観点 22: 割込み - 登録と参照
- **対象**: 登録処理中の参照リクエスト
- **狙うバグ**: トランザクション管理不備、データ不整合

---

## 観点 16: N/A

「設定保持(終了後の保持)」は対象システムにブラウザ閉じても残る設定がある場合のみ
適用。Webアプリの一般的な予約フォームなどでは N/A としてスキップ可。

## エージェントへの指示

- 観点を選んだら、必ず「対象」「考慮すべき仕様」「狙うバグ」を `reports/session-log.md`
  に書き出してから、テスト設計に入る
- 「狙うバグ」を1つも特定できない観点は、その理由を記録してスキップしてよい
  (例: 該当機能なし、対象システムに該当する操作がない)
- 各観点で生成するテストは2〜5ケース。**境界値・異常値を必ず1件以上含める**
- 観点27・28は、環境制約で自動化できない場合に **N/A で閉じず**、
  `manual-tests.md` に手順を起票して「手動テスト待ち」にすること。
  (別アカウントが用意できない / サーバ時刻を動かせない は N/A の理由にならない)
